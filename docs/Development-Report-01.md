## Architecture Decisions

Approved by the Product Owner during this task:

1. **Framework**: Next.js 15, App Router.
2. **CMS**: Payload CMS 3, embedded in the Next.js app (single deployable, shared types, self-hosted).
3. **Database**: PostgreSQL.
4. **Styling**: Tailwind CSS v4 over CSS-variable design tokens; runtime-overridable per event for CMS-driven theming.
5. **Auth**: Payload built-in authentication with a centralized RBAC permission layer.
6. **Default locale**: per-event, defined in the CMS (`Event.defaultLocale`). `he` serves as technical routing fallback only.

Made within approved boundaries (documented, reversible):

7. **i18n split**: content localization in Payload (document-level), UI chrome in next-intl (message catalogs). Locale-prefixed routing via middleware.
8. **Scene registry pattern**: scene types resolve through a typed registry; unknown types degrade gracefully. Scene type ids remain open strings until the scene catalog is approved.
9. **Scene ordering on Experience**, not on Scene — scenes are reusable across experiences.
10. **Access control via permission factories** — collections never contain inline role logic.

## Risks

1. **Version drift** — pinned ranges (Next 15, Payload 3, Tailwind 4) should be locked to exact versions at install time.
2. **Scene content modeling** — flexible scene content must be modeled per scene type (Payload blocks vs. per-type collections). Decided when the scene catalog is approved.
3. **Government hosting constraints** — deployment environment (cloud vs. on-prem) affects caching, media storage, and CDN strategy. Unknown at this time.
4. **Load target** — the 600-concurrent-user target requires a caching strategy that will be validated with load testing once rendering exists.

## Questions Before Next Task

Decisions identified during this task that require Product Owner approval. No assumptions were made; development stopped at the approved boundary.

1. **Scene type catalog** — which initial scene types does the platform ship with (e.g., hero, agenda, speakers, sponsors, registration, custom-content)? This defines the CMS content schemas and the first renderer work.
2. **Role matrix** — beyond `admin` and `editor`: are per-event editors, registration managers, or read-only reviewers required? Affects the permissions model and event-scoped access.
3. **Deployment environment** — cloud (which provider?) or on-premises? Affects media storage (local vs. S3-compatible), CDN/caching, and the migration workflow.
4. **Registration model** — will participant registration be handled inside the platform (participants as CMS users vs. a separate participants collection) or via external systems? Affects auth architecture before the registration feature is specified.
